# シミュレーションコア・ゲートウェイ間プロトコル設計書

## 1. 所有者

本プロトコルの所有者はシミュレーションコアです。

理由は、シミュレーションコアとゲートウェイのうち、シミュレーションコアの方がシステム中心側に位置し、外部へ公開可能な状態と受理可能な管理操作の意味を定義する責任を持つためです。

## 2. 目的

本プロトコルは、シミュレーションコアと複数のゲートウェイ間で、以下を行うための契約を定義します。

- 外部参照用シミュレーション状態の配信
- ゲートウェイキャッシュ更新に必要な情報の提供
- 管理ビュー由来の管理要求の受理
- 管理要求に対する結果の返却
- コアの公開可能な実行状態・診断状態の通知

## 3. 設計原則

- ゲートウェイはコアのコード、DLL、内部型を参照しない。
- コアはゲートウェイのコード、DLL、内部型を参照しない。
- 双方は本プロトコル設計書だけを契約として実装する。
- コア内部の可変状態をプロトコル越しに直接公開しない。
- コアの内部データ構造と通信データ構造を同一視しない。
- 1つのコアに複数ゲートウェイが接続することを前提とする。
- 外部参照負荷をコアへ直接集中させない。

## 4. 主要な通信カテゴリ

### 4.1 状態配信

シミュレーションコアからゲートウェイへ、外部公開可能な状態を提供します。

ゲートウェイは受信した状態を参照用キャッシュへ反映します。

具体的な Push / Pull、全量 / 差分 / スナップショット、更新頻度、順序保証は未確定です。

### 4.2 管理要求

管理ビューからゲートウェイへ送られた管理要求のうち、コアへ影響するものをゲートウェイからコアへ伝達します。

コアは要求を受理した後、シミュレーション上の整合性と実行可否を最終判断します。

### 4.3 管理結果

コアは管理要求の処理結果をゲートウェイへ返します。

成功・拒否・競合・一時的失敗・恒久的失敗など、具体的な結果分類は今後定義します。

### 4.4 実行状態・診断状態

管理ビューで必要となるコアの実行状態や診断情報を、ゲートウェイが取得または受信できる契約を定義します。

## 5. バージョニング

プロトコル変更はコア側の実装変更だけで暗黙的に行いません。

変更時は本設計書を先に更新し、ゲートウェイが独立して追従できる状態を作ります。互換性を破る変更を行う場合の版管理方式は今後定義します。

## 6. 並行開発条件

コアとゲートウェイは、同時に別担当者が実装してもソースファイル競合を起こさないことを前提とします。

双方は本設計書に基づくスタブやテスト用通信相手を用いて、相手実装が未完成でも独立して開発・テストできる構造を目指します。
