# 要件定義 Q200〜Q279

この文書は、対話ベースの要件定義で確定した質問と回答結果を要件番号順に保持します。質問文は要件として意味が変わらない範囲で要旨化し、回答結果は確定時の選択とカスタム指定を保持します。

| Q | 質問 | 回答結果 |
|---:|---|---|
| 200 | Coreの時間進行を可変dtにするか固定Stepにするか | C。固定World Time Stepを権威ある計算基準とし、標準30Hz。実時間追従を目標とし、倍率変更、Pause、低速・高速化をConfig/Admin操作で可能にする。調整数値はConfig。 |
| 201 | 並列処理の完了順を状態適用順にしてよいか | C。`State(T) → 並列読み取り・計算 → 決定論的マージ → State(T+1)` とし、タスク完了順を適用順にしない。 |
| 202 | 同一時刻のイベント順序をどうするか | C。必要な場合は安定した決定論的順序を持つ。具体的な順序キーは詳細設計で決定。 |
| 203 | 外部Operationを物理到着時刻で即適用するか | C。Gateway到着時刻そのものではなく、決定論的なWorld Time/Stepへ割り当てる。 |
| 204 | 30Hzに間に合わない場合にStepを飛ばすか | C。処理超過だけを理由に世界Stepを飛ばさない。決定論を優先し、実時間から遅れてもよい。遅延・負荷・詳細度方針はConfig。 |
| 205 | 乱数をどう決定論化するか | C。World Seed＋World Time＋対象・用途等の論理コンテキストでアドレス可能な乱数とし、共有状態PRNGの消費順へ依存しない。 |
| 206 | Entity IDをどうするか | C。保存・再開・リプレイを通じた永続IDを持ち、スレッド順・非決定論的生成順に依存しない。後にQ266で生成規則を補足。 |
| 207 | 並列集約をどうするか | C。世界結果へ影響する集約は決定論的に行い、Coreのスレッド数を1〜16で変えても同一条件なら同一結果にする。 |
| 208 | CPU/OS/runtimeを跨いだ浮動小数のビット完全一致を要求するか | B。論理的決定論は強く要求するが、異なるCPU/OS/runtime間の全浮動小数演算のビット単位一致は標準要件としない。 |
| 209 | 決定論違反の検出をどうするか | C。当初、同一条件の反復実行と状態ハッシュ等による自動整合性検証を要求。後のQ252で、標準はハッシュ比較までをB相当、高度な自動局所化はアドオンへ整理。 |
| 210 | Configをどのように分類するか | C。少なくともシミュレーション影響Configと表示・運用のみのConfigを区別し、さらに再起動必須、世界再生成必須、実行時変更可能等の変更可能性を分類する。 |
| 211 | 実行中Config変更をどう適用するか | C。明示的な安全境界で原子的に適用し、世界影響変更はWorld Time/Stepと結び付け、履歴に記録してリプレイ可能にする。 |
| 212 | Config不整合時にどうするか | 「基本的にCだけど、不整合があればそもそも起動しないで。」型・範囲・相互制約を検証し、起動時Configに不整合があればコンポーネント/世界を起動しない。実行中の無効変更セットは原子的に拒否する。 |
| 213 | 他コンポーネントへ影響するConfigをどう扱うか | 「他コンポーネントに影響するようなConfigファイルは用意しないし、他コンポーネントに影響するものはコアに近いコンポーネントが配布する。」Configファイルは各コンポーネントが独立所有し共有しない。境界を越えて必要な設定・状態はCoreに近い側がプロトコルで配布する。 |
| 214 | 古いConfigファイルの互換性をどうするか | 「Configは下位互換を設けて、バージョンが古く項目が少ない場合はデフォルト値をConfigファイルに追加する。」古いConfigで新規項目が欠ける場合、既定値を補いConfigファイルへ追記する。 |
| 215 | Operationを再送・切替で追跡する識別子を持つか | C。全hop、再送、failover、reconnectを通して不変の一意Operation IDを持つ。 |
| 216 | Operationの重複適用をどう防ぐか | C。End-to-Endでdedup/idempotencyを保証し、同一Operation IDが世界へ2回影響しない。 |
| 217 | Master切替の世代をどう扱うか | C。Master generation/epochを持ち、Coreが正当性を決定し、旧Master世代の出力を拒否する。 |
| 218 | ACK消失時の再送をどうするか | C。同一Operation ID/Batch IDで安全に再送し、再送回数・タイミング・順序が世界結果を変えない。 |
| 219 | 複数Gatewayの操作順をどう決めるか | C。各Gateway内の順序とMaster mergeを決定論化し、同じ有効Operation集合ならGateway数、ネットワーク、Master、スレッド順に依存せず同じCore順序にする。 |
| 220 | Master候補の条件をどうするか | C。単に接続中だけでなく、応答可能、プロトコル互換、必要Capability、同期状態等、安全に役割を担える条件を満たすGatewayだけを候補にする。 |
| 221 | Master障害をどう判定するか | C。heartbeat/応答遅延等から判定し、監視間隔、失敗判定時間、再選出条件等は外部Config。瞬間的遅延と障害を区別する。 |
| 222 | Master切替で未完了処理をどうするか | C。「ライブマイグレーションに耐える設計で」。未完了Batch、ACK待ち、再送中Operationを新世代へ安全に引き継ぎ、欠落・重複を起こさず、live migrationにも耐える。 |
| 223 | Operation受信期限をどうするか | C。World Time/適用Step単位のdeadlineを持ち、deadline、grace、late処理はConfig化し決定論的に扱う。 |
| 224 | 遅れて届いたOperationで過去を書き換えるか | C。過去の確定状態をretroactiveに書き換えず、次以降の有効Stepへ繰越すか、プロトコル定義に従い延期・拒否する。 |
| 225 | 非Master Gateway切断時の未確定Operationをどうするか | C。保持し、同一Operation IDで再接続・Master変更・世代変更を跨いで再送可能にし、重複排除する。 |
| 226 | Gateway再接続時のキャッシュをどうするか | C。古いキャッシュをそのまま信頼せず、Coreまたはプロトコル上の権威ある同期元から基準World Time/世代等を確認して再同期してから通常公開する。 |
| 227 | Gatewayキャッシュ喪失・不整合をどう扱うか | C。Coreのみが正本。Gatewayキャッシュは派生物であり、異常時は検出・破棄・再構築する。キャッシュ喪失を世界喪失にしない。 |
| 228 | 約1秒遅延をどう実装意味付けするか | C。単純sleepではなくWorld Time範囲を保持する論理的な公開バッファとし、jitter・順序を安定化する。長さはConfig。cacheとは別責務。Core 30Hzと公開30Hzを同一視しない。 |
| 229 | 欠落・順序不整合・再同期中の公開をどうするか | C。異常を検出して再取得し、不整合な状態列を通常状態として公開しない。再同期中であることを接続ユーザーへ通知し、General Viewで明示表示する。 |
| 230 | General Viewの表示基準をどうするか | C。Gatewayが公開する確認済み状態を明示的な表示World Timeと共に使い、互換性のない異なるWorld Timeの状態を混在させない。 |
| 231 | View側の補間・予測を許可するか | C。滑らかな表示のため補間・短期予測を許可するが、表示専用で非権威。予測状態と確認済み状態を区別可能にする。 |
| 232 | Diver操作の体感遅延をどうするか | C。「ダイバー目線ではリアルタイムに操作しているような体験にしてもらいたい」。Diver操作ではローカル予測・補正を許容し、Core確定状態へreconcileする。予測は世界結果を変えない。 |
| 233 | General View再接続時の状態復帰をどうするか | C。可能ならsessionを復元し、Gatewayの基準World Timeへ同期してから通常表示し、同期中状態を表示する。 |
| 234 | Diver切断中の住人をどうするか | 「基本はCだがD。通常切断でもエラー切断でも同様に処理、不在時にどういった行動を優先させるかはダイバーがあらかじめ決めれる。」世界内住人は切断中も存在・行動し、巻き戻さない。切断種別で特別扱いせず、不在中の行動優先方針をDiverが事前設定可能にする。 |
| 235 | Admin操作の妥当性確認をどこが担うか | 「Cだが、妥当性チェックはゲートウェイが担う。」Admin View→Gateway→Coreとし、Admin操作固有の妥当性チェックはGatewayが担う。後にQ275でCoreの一般状態不変条件との境界を明確化。 |
| 236 | Admin操作を常に最優先にするか | 「基本Cだが、シミュレーションに影響が出ないものに限ってAdmin操作が最優先」。シミュレーション影響Admin操作は無条件最優先にしない。 |
| 237 | 高影響Admin操作の安全策をどうするか | C。追加確認、監査、結果記録を要求し、具体的分類・UXは詳細設計で決定。 |
| 238 | Admin監査に何を残すか | C。誰が、いつ、何を、Operation ID、対象、要求、適用World Time、結果、拒否理由、関連Config変更等を追跡可能にし、リプレイ・障害調査と関連付ける。 |
| 239 | Admin操作にUndoを設けるか | 「Dで所謂Undoは設けず、もとの設定に戻す操作を新たに実行するものとする。」履歴を消すUndoは持たず、元へ戻す場合も新規Operationとして実行・監査する。 |
| 240 | General ViewとAdmin Viewの認証・認可ドメインをどうするか | C。明確に分離し、一方の権限を他方へ自動付与しない。技術的な共通外部認証基盤を使う可能性は妨げない。 |
| 241 | Gatewayの認可とログイン処理をどうするか | C。「ログイン処理はゲートウェイにプロキシされてマスターで行う」。接続先Gatewayはログイン要求をMasterへproxyし、Masterでログイン処理を行う。非Masterが独自に認証確定しない。 |
| 242 | 接続中のロール変更をどうするか | C。明示的な有効時点を持ち、変更前後のOperationを区別し監査する。到着競争・スレッド順に依存させない。 |
| 243 | 権限剥奪を既存sessionへどう反映するか | C。新規Operationへ即反映し、重大な剥奪では既存session/credentialを無効化可能にする。古い権限で新規操作を継続させない。 |
| 244 | 認証基盤障害時にfail-openするか | C。認可を迂回しない。新規loginを停止し、既存sessionは明示的な安全grace内のみ継続可能。高影響操作はfail-safe。数値はConfig。 |
| 245 | Minor差接続をどう扱うか | C。同一MajorではMinor差を許容し、新しいMinorは後方互換を維持する。接続時にMinorと対応Capabilityを交換し、必要機能不足を明示する。 |
| 246 | Capability Negotiationで何を交換するか | C。「アドオンに関しても情報交換が必要」。必須/任意Capabilityを交換し、必要Capability不足は接続・機能拒否。アドオンの互換性・接続安全性に必要な情報も交換する。 |
| 247 | 新Minorから旧Minorへ未知内容を送るか | C。相手Capabilityに応じて送信内容を選び、古い相手が理解できない内容を無条件送信しない。安全に無視できる未知項目と意味的不整合を区別する。 |
| 248 | Major不一致時の診断をどうするか | C。接続拒否し、理由、双方version、必要な更新方向を利用者・運用者が確認可能にする。 |
| 249 | 接続中にCapabilityが変化した場合どうするか | C。再接続時を基本の再Negotiation点とし、live migration、Master切替、addon変更等で変化する場合は安全な再Negotiationまたは接続再確立を行い、意味を黙って変えない。 |
| 250 | ログ形式をどうするか | C。各コンポーネントは構造化ログを基本とし、必要に応じcomponent、instance、World Time、Operation ID、Batch ID、Master generation等の文脈を付与する。 |
| 251 | 監視対象をどうするか | C。CPU/Memory/Connection等に加え、処理時間、queue、error、reconnect、sync、World Time lag、30Hz目標差、publication buffer、resync、Master state/generation、retry/dedup等を監視可能にする。 |
| 252 | 決定論診断を標準でどこまで行うか | B、Cはアドオン。標準は定期・検証時のWorld State hash等による不一致検出まで。詳細な自動局所化、Operation/Config/World Time相関解析は将来アドオン。 |
| 253 | ログ保持をどうするか | C。保持期間、容量、rotationをコンポーネント別・ログ種別別の外部Configで管理し、監査ログと大量診断ログを同一条件に固定しない。 |
| 254 | Admin Viewで何を監視するか | C。component health/主要metricsに加え、Master state/generation、resync Gateway、protocol/Capability mismatch、Core lag、Config error、retry増加、save/recovery状態等を確認可能にする。 |
| 255 | アドオンがコンポーネント境界・標準プロトコルへどう影響してよいか | D。「コンポーネント単位でアドオンを設定できるようにする。標準プロトコルにアドオンのための機能は一切載せない（アドオンのインストール状況なんかのやり取りは標準プロトコルに乗せる）。その代わりにプロトコルのアドオン、もといアドオンの前提フレームワークアドオンなどで、アドオンに使える情報を載せたプロトコルを用意する。」標準プロトコルはメタ情報のみ。アドオン固有機能データは追加プロトコル側へ分離。 |
| 256 | アドオン互換性をどう判定するか | C。対象component/protocol version、required/provided Capability、依存addon情報を宣言・検証し、不足・非互換なら有効化しない。 |
| 257 | アドオン構成に不整合がある場合どうするか | Cを強化。「重大じゃなくても起動拒否」。addon、依存、Config、Capability等の不整合を検出したら重大度に関係なくコンポーネントを起動しない。自動縮退起動を標準にしない。 |
| 258 | アドオン更新をどうするか | C。自動即時更新ではなく明示操作。適用前に互換性、Capability、依存、Config影響を確認し、simulation影響変更は安全なWorld Time/Step/restart境界で適用する。 |
| 259 | アドオン無効化・削除をどうするか | C。依存関係を確認し、世界・保存データへ永続影響がある場合は移行・restart・互換性を判定し、単純削除で世界整合性を壊さない。 |
| 260 | Diverを新規専用住人として生成するか | 「C（ただし新規はなし）」。Diverは既存の通常住人Entityへ紐付く。Diver専用の新規住人を参加時に生成しない。操作中も通常の物理・社会・経済・法・健康等の世界ルールに従う。 |
| 261 | Diverが操作住人をどう選ぶか | 「C（ただし新規はなし、大まかな要求はできるが、叶うかどうかは別）」。既存住人だけを対象とし、Diverは大まかな希望条件を提示できるが、条件に合う住人が割り当てられることは保証しない。無条件の任意乗っ取りは不可。 |
| 262 | 同一住人を複数Diverが同時操作するか | 「B（切断後も操作ダイバーは変わらない）」。原則1住人につき1Diver。切断しても、その住人を操作するDiverの対応関係を別Diverへ自動変更しない。 |
| 263 | 再接続時にDiver識別を変えてよいか | 「D（必ず同じダイバーを使う）」。通常切断・再接続を跨いでも必ず同じDiver識別を使用する。 |
| 264 | 操作中住人が死亡した場合どうするか | C。死亡住人は通常の死亡、相続、記録、社会影響等に従う。Diver自体は同一識別を維持し、再参加は世界・参加ルールに従って既存住人へ紐付ける。 |
| 265 | Q083とQ190/Q193をどう整合させるか | C。世界規模で個体の存在、永続ID、重要な永続状態を保持可能にする一方、「個体として存在すること」と「高頻度・高詳細度で更新すること」を分離する。遠隔・低重要度対象は更新頻度・詳細度を落とせる。 |
| 266 | 未来に生まれる住人等のIDを世界生成時に全予約するか | C。未来の全IDを事前列挙しない。出生・生成事象の決定論的コンテキストからIDを生成し、スレッド順・処理順・環境に依存しない。 |
| 267 | 保存世界が依存するアドオンに不一致がある場合どうするか | C。必要addon/version/Capabilityに不整合があれば世界を起動しない。明示的なmigrationが完全成功し整合性確認できた場合のみ起動可能。 |
| 268 | 接続Gatewayが0台になった場合Coreを止めるか | C。Gateway不在だけを理由にCore World Timeを止めない。受理済みOperation・内部eventを予定通り処理し、新規外部Operationだけ入らない。復旧後に不在期間を巻き戻さない。 |
| 269 | Master Gateway選択そのものを再現可能にするか | C。Master選択結果自体の再現性は標準要求しない運用ランダムでよい。ただし選択結果・世代は記録可能にし、どのMasterでも同じ有効Operation集合なら世界結果は同じ。split-brain防止は必須。 |
| 270 | 保存中にsimulationを止めるか | 「C（処理負荷が高いときは停止してもよい）」。原則進行中でも特定World Time/Stepの一貫Snapshotを取得可能にするが、安全な一貫保存が高負荷・困難な場合は整合境界で停止して保存してよい。停止有無で世界結果を変えない。 |
| 271 | 保存データ破損時に部分読込で続行するか | C。破損保存点を拒否し、正常なSnapshot＋Operation履歴等から可能な限り最新確定状態まで決定論的に復旧する。不整合状態では起動しない。 |
| 272 | 保存時Configと現在Configの差をどう扱うか | C。保存世界が要求するsimulation影響Configを保持し、現在Configとの差を分類する。再現性を壊す不整合は無条件続行せず、必要なら明示migrationを要求する。 |
| 273 | 古い保存形式をどう扱うか | C。可能な後方互換を持ち、直接読めない旧形式には明示的・決定論的migration経路を用意可能にする。変換不能なら起動拒否し、黙って情報を捨てない。 |
| 274 | 復旧後を別世界として扱うか | C。同じ確定状態と入力履歴から同じ因果系列を継続し、Entity ID、World Time、適用済みOperation等を維持する。 |
| 275 | GatewayのAdmin妥当性確認とCoreの状態検証をどう分けるか | C。GatewayがAdmin権限、操作形式、対象、許可条件等を検証する。CoreはAdminロールを解釈せず、全操作共通の世界状態不変条件・状態遷移整合性を維持する。Gateway許可だけで不整合状態を作らない。 |
| 276 | 外部Operationの最終適用Stepを誰がどう決めるか | C。Gateway/Masterがprotocol規則に従い候補適用時刻を形成し、Coreが現在World Time、deadline、generation、ordering rules等から最終有効Stepを確定する。通信速度・raceだけで結果を変えない。 |
| 277 | World Timeの権威ある内部表現をどうするか | C。整数ベースのSimulation Stepを権威ある時間軸とし、秒・日時等は必要に応じ変換する。社会的暦・表示時刻・住人時刻認識とは分離する。 |
| 278 | Pause中に届いたOperationをどうするか | C。受信、認証、認可、queue保持は可能。simulation影響OperationをPause中の止まったWorld Timeへ曖昧適用せず、Resume後の明示的有効Stepへ決定論的に割り当てる。非simulation運用操作は別扱い可能。 |
| 279 | 通貨供給・金融政策を標準で扱うか | C。通貨発行、供給量、発行主体、基本的な金融政策を標準で扱う。ただし現代中央銀行を普遍前提にせず、社会・時代ごとに発行主体・供給調整制度が異なり、歴史的に形成・変化・競合・衰退し得る。高度金融市場・高度金融政策はアドオンへ拡張可能。 |

## 最終的な横断解釈

- 後続Qで解消された旧記述は、旧回答を削除するのではなく「当時の決定」として履歴に残し、現在の有効要件は後続Qを優先する。
