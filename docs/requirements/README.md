# MachiVerse 要件定義

## 目的

このディレクトリは、対話ベースの要件定義で確定した質問と回答結果を、実装や個別設計書から独立した要件記録として保持するための正本です。

設計書は要件を説明・具体化するために更新されますが、設計書の古い記述によって確定済み要件を暗黙に取り消してはなりません。

## 要件記録

- [Q001〜Q099](requirements-qa-001-099.md)
- [Q100〜Q199](requirements-qa-100-199.md)
- [Q200〜Q279](requirements-qa-200-279.md)

各項目は、質問番号、質問の意味内容、回答結果、必要に応じて回答時のカスタム指定を対応付けます。

この文書群はチャットUIの逐語トランスクリプトではありません。要件定義として使用できるよう、質問の意味内容と確定した回答結果を崩さずに整理した決定記録です。回答にカスタム指定が含まれた項目は、その指定を優先して記録します。

## 優先順位

要件または設計書同士に見かけ上の矛盾がある場合は、次の順序で解釈します。

1. 後の質問で明示的に以前の決定を補足・変更・解消した場合は、後の確定回答を優先する。
2. `docs/requirements` の確定要件を、個別のアーキテクチャ設計書にある古い記述より優先する。
3. プロトコルの具体的な通信契約については、確定要件に反しない範囲で `docs/protocols` を契約の正本とする。
4. `今後決定が必要な事項` や `TBD` は、確定要件と矛盾しない詳細設計上の未決事項として扱う。既に後続質問で決定済みの事項をTBDとして残さない。
5. 将来アドオンの可能性は、標準実装の確定要件を弱めたり、未確定のアドオンAPIを標準要件として先取りしたりする根拠にしない。

## 横断原則

要件全体を読む際は、少なくとも次の原則を常に適用します。

- 標準構成は単一Simulation Coreであり、Coreが世界状態の正本を持つ。
- Core、Gateway、General View、Admin Viewはコード・ビルド・実行・配布単位で独立し、コンポーネント間はプロトコルのみで連携する。
- 世界状態へ影響する処理は決定論を守り、処理速度、スレッド実行順、OSスケジューリング、Gateway数、Master個体等を暗黙の結果決定要因にしない。
- 権威あるWorld Timeは整数ベースのSimulation Stepとする。
- 調整可能な数値は責任コンポーネントの外部Configで管理する。Configファイルをコンポーネント間で共有しない。
- 標準プロトコルにアドオン固有機能データを載せない。接続安全性・互換性確認のためのアドオンメタ情報のみ標準プロトコルで交換できる。
- 3Dは表示だけではなくSimulation Coreの権威ある世界モデルに適用する。
- Diverは新規専用住人を生成せず、世界内に既に存在する通常住人へ紐付く。
