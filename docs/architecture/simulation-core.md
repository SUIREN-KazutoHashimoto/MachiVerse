# シミュレーションコア設計

## 1. 目的

シミュレーションコアは、MachiVerse におけるシミュレーションそのものの実行責任を持つ領域です。

UI、外部クライアント数、画面更新頻度、外部からの高頻度参照などの事情から隔離し、シミュレーション計算へ専念できることを重要な設計目標とします。

シミュレーションコアは他コンポーネントとコード依存を持たず、独立したビルド・配布・実行単位として扱います。

## 2. 主な責務

- シミュレーション状態の正本保持
- シミュレーション時間の進行
- エージェント状態の保持と更新
- 環境状態の保持と更新
- シミュレーションルールの適用
- 状態遷移の実行
- 内部イベントの処理
- ゲートウェイから受け付けた有効な管理要求の反映
- 外部参照用状態の提供
- 実行状態の管理
- シミュレーションコア・ゲートウェイ間プロトコルの所有

## 3. 責務外

- 一般ビュー・管理ビューとの直接通信
- 外部クライアント接続管理
- 一般利用者からの参照要求への個別応答
- 外部向け負荷分散
- UI 用の表示形式への変換
- ゲートウェイキャッシュの管理
- ゲートウェイ実装コードの管理
- 一般ビュー・管理ビュー向けプロトコルの所有

## 4. ゲートウェイとの関係

シミュレーションコアとゲートウェイは 1 対多の関係です。

```text
                 ┌─ ゲートウェイ A
シミュレーション ├─ ゲートウェイ B
コア             ├─ ゲートウェイ C
                 └─ ...
```

コアは複数ゲートウェイへ外部公開可能な状態を提供できる境界を持ちます。ただし、一般ビューや管理ビューからの参照要求ごとに同期的な問い合わせ処理を行うことを前提にしません。

ゲートウェイ側が参照用状態をキャッシュすることで、外部の読み取り負荷をコアから分離します。

## 5. コード・実行単位の分離

シミュレーションコアは、ゲートウェイ、一般ビュー、管理ビューのいずれともコード共有を行いません。

禁止する依存は以下です。

- 他コンポーネントへのプロジェクト参照
- 他コンポーネント DLL の参照
- 共通 DTO ライブラリによる通信契約の共有
- 他コンポーネント内部型の参照
- 同一プロセス内の直接メソッド呼び出し

シミュレーションコアは独立した実行ファイルまたは実行単位とし、ゲートウェイが未完成または停止中でも、コア単体のビルド・テスト・実行が可能な構造とします。

## 6. プロトコル所有責任

シミュレーションコアは、ゲートウェイとの通信に用いるプロトコルの所有者です。

対象設計書は `docs/protocols/core-gateway.md` です。

コアは、外部公開可能な状態、受理可能な管理操作、通信上の意味、互換性、変更方針をこの設計書で定義します。

ゲートウェイはコアの内部コードや内部型に依存せず、このプロトコル設計書を契約として独立実装します。

プロトコル変更が必要な場合、コア実装だけを変更して暗黙的に契約を変えるのではなく、まずプロトコル設計書を更新します。

## 7. 主要機能

### 7.1 実行状態管理

シミュレーションが現在どの実行状態にあるかを管理します。

具体的な状態一覧と遷移規則は今後定義します。

### 7.2 時間進行

シミュレーション内部の時間を進めます。

時間進行方式、Tick の有無、固定時間刻み・可変時間刻み・イベント駆動などは未確定です。

### 7.3 エージェント管理

シミュレーションに存在するエージェントの状態を管理します。

具体的なエージェント種別、属性、生成・消滅条件、更新頻度、所属関係などは今後定義します。

### 7.4 環境管理

エージェントが存在・行動するシミュレーション環境の状態を管理します。

環境表現の具体方式は未確定です。

### 7.5 ルール実行

エージェントや環境へ適用されるシミュレーションルールを実行します。

ルールは UI、ゲートウェイ、通信方式に依存させません。

### 7.6 内部イベント処理

シミュレーション内部で発生する状態変化や通知をイベントとして扱う場合、その生成・処理順序・反映責任を管理します。

### 7.7 管理要求の受理

管理ビューからの管理操作は、必ずゲートウェイを経由し、コア・ゲートウェイ間プロトコルに従ってコアへ到達します。

コアは受け取った要求について、シミュレーション上の整合性と実行可否を最終判断します。ゲートウェイで認証・認可済みであっても、シミュレーション上不正な状態遷移をコアが無条件に受け入れることはありません。

一般ビューはリードオンリーであるため、一般ビュー由来の状態変更要求をコアへ到達させません。

### 7.8 外部参照用状態の提供

ゲートウェイがキャッシュを構築・更新できるよう、コア・ゲートウェイ間プロトコルに従って外部公開可能な状態を提供します。

重要な原則は次の通りです。

- コア内部の可変データ構造を直接公開しない。
- 外部参照の頻度をシミュレーション計算頻度と密結合させない。
- 外部クライアント数に応じてコアの参照処理量が線形増加しない構成を目指す。
- 状態提供方式は、コアの主要計算処理を過度に阻害しないものとする。

具体的な Push / Pull、全量 / 差分、スナップショット等の方式は未確定です。

## 8. データ所有権

シミュレーションの正本となる状態はシミュレーションコアが所有します。

ゲートウェイが保持するキャッシュ、一般ビュー・管理ビューが保持する表示用データは正本ではありません。

外部側のキャッシュ状態とコアの状態に差がある場合、コアの状態を正とします。

## 9. 読み取り負荷からの隔離

超大規模運用では、多数の一般ビュー・管理ビューから大量の参照要求が発生する可能性があります。

コアはそれらに個別応答するサーバーとして設計せず、計算結果をゲートウェイがキャッシュ可能な形で提供する側に徹します。

これにより、利用者数の増加、ビューの更新頻度、画面数の増加が、シミュレーション計算量へ直接反映されることを防ぎます。

## 10. 管理操作の境界

管理操作の経路は以下に固定します。

```text
管理ビュー -> ゲートウェイ -> シミュレーションコア
```

次の経路は禁止します。

```text
管理ビュー -> シミュレーションコア
一般ビュー -> シミュレーションコア
一般ビュー -> ゲートウェイ -> シミュレーションコアへの状態変更
```

## 11. 並行開発

シミュレーションコアはゲートウェイと同時並行で実装できることを前提とします。

通常の機能実装で両者が同一ソースファイル、同一プロジェクトファイル、共通 DTO 実装を編集する構造は禁止します。

ゲートウェイ実装が未完成でも、コアはプロトコル設計書に基づくテスト用通信相手を利用して独立テストできる構造を目指します。

## 12. 超大規模化における設計要件

- 外部参照処理よりシミュレーション計算を優先できる構造とする。
- 状態更新の並列化を検討可能にする。
- 処理単位の分割を検討可能にする。
- 一部処理の分散化を阻害しない。
- 大量エージェントを効率的に保持できる構造を検討する。
- 状態参照と状態更新の競合を低減する。
- スナップショット取得を検討可能にする。
- 再現性を確保できる余地を残す。
- ボトルネックを計測可能にする。
- ゲートウェイ台数や外部クライアント数をコア内部ロジックが意識しない構造とする。

## 13. 禁止する依存

- 他コンポーネントへのコード参照
- 他コンポーネント DLL への依存
- 共通 DTO ライブラリによる境界共有
- UI フレームワークへの依存
- 一般ビュー・管理ビューへの依存
- ゲートウェイ実装への依存
- ビュー都合の DTO や画面構造をコアのドメインモデルとして扱うこと
- 外部層からコア内部の可変状態を直接変更させること
- 一般ビュー由来の状態変更要求を受理すること
- 個々のビュー要求へコアが直接応答する構成を前提にすること
- プロトコル設計書に存在しない暗黙仕様への依存

## 14. 今後決定が必要な事項

- エージェントモデル
- 環境モデル
- 時間進行モデル
- 更新順序
- 並列実行単位
- 分散実行の有無
- 決定性・再現性要件
- 乱数管理方式
- スナップショット方式
- 永続化との境界
- 管理操作の整合性規則
- 外部参照用データの粒度
- コアからゲートウェイへの状態配信方式
- 状態配信頻度
- 全量配信と差分配信の使い分け
- 実際の通信技術
- シリアライズ形式
- プロトコルバージョニング方式
