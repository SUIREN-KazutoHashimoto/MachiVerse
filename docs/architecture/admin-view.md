# 管理ビュー設計

## 1. 目的

管理ビューは、MachiVerse の運用者・管理者がシミュレーションおよびシステム全体の状態を監視し、必要な管理操作を行うための領域です。

管理ビューはシミュレーションコアへ直接接続せず、参照・管理操作のすべてをゲートウェイ経由で行います。

## 2. 主な責務

- シミュレーション実行状態の監視
- システム稼働状態の監視
- 管理者向け操作の受付
- ゲートウェイへの管理要求送信
- 管理情報・診断情報の表示
- 障害・異常状態の表示
- 負荷・処理状況の可視化
- 運用設定変更の入口
- 監査可能な管理操作を行うための UI 境界

## 3. 責務外

- シミュレーションルールそのものの実装
- シミュレーション状態の正本管理
- コア内部状態の直接変更
- シミュレーションコアへの直接接続
- 認証・認可の最終判定
- 負荷分散や接続ルーティングの実装
- 一般利用者向け表示機能の主担当

## 4. 主要機能

### 4.1 シミュレーション実行状態監視

シミュレーションが稼働中か、停止中か、異常状態かなど、運用上必要な状態を確認できるようにします。

通常の参照情報はゲートウェイの参照用キャッシュから取得できる構成を基本とします。

### 4.2 システム状態監視

シミュレーションコアだけでなく、複数ゲートウェイを含む周辺領域の状態も把握できることを目標とします。

監視対象として想定される情報には以下があります。

- 稼働・停止状態
- 処理遅延
- エラー発生状況
- 接続数
- 要求量
- シミュレーション処理負荷
- リソース使用状況
- ゲートウェイごとのキャッシュ状態

具体的なメトリクスは今後定義します。

### 4.3 管理操作

管理ビューは、ゲートウェイを経由してシミュレーションコアへ管理操作を要求できます。

管理ビュー自身がコア状態を書き換えることはありません。管理操作は必ず以下の経路を通ります。

```text
管理ビュー -> ゲートウェイ -> シミュレーションコア
```

ゲートウェイは管理要求の認証・認可・形式検証・仲介を行い、シミュレーション上の最終的な妥当性判断と状態変更はコアが担当します。

将来的に考えられる操作例として、開始、停止、一時停止、再開、設定変更などがありますが、実際に提供する操作は要件確定後に定義します。

### 4.4 設定管理

運用中に変更可能な設定が存在する場合、その確認・変更を行う UI を提供します。

設定変更要求もゲートウェイを経由し、管理ビューからコアへ直接反映しません。

### 4.5 障害・異常表示

システム内で発生した異常や、運用者が対応すべき状態を表示します。

### 4.6 診断情報表示

性能問題や障害調査に必要な診断情報を閲覧できるようにします。

管理ビュー自身が診断データの正本になるのではなく、ゲートウェイ経由で取得した情報を表示します。

### 4.7 管理操作の監査

影響範囲の大きい管理操作について、誰が、いつ、何を行ったかを追跡できる仕組みを配置可能にします。

具体的な監査ログ方式は今後決定します。

## 5. 読み取りと管理操作の違い

管理ビューには、参照と管理操作の2種類があります。

### 5.1 参照

監視や診断のための参照です。即時の正本確認が不要な情報は、ゲートウェイのキャッシュから取得できます。

### 5.2 管理操作

シミュレーション状態へ影響を与える要求です。キャッシュを書き換えるのではなく、ゲートウェイからコアへ管理要求として伝達します。

管理操作による状態変更後、その結果は通常の状態公開・キャッシュ更新経路を通して各ゲートウェイへ反映されます。

## 6. データ所有権

管理ビューが所有するのは、画面表示や操作途中の UI 状態のみです。

シミュレーション状態の正本はコアにあります。ゲートウェイのキャッシュも管理ビュー上の表示データも正本ではありません。

## 7. 他領域との関係

### ゲートウェイ

- 管理ビューはゲートウェイにのみアクセスする。
- 状態参照はゲートウェイ経由で行う。
- コアへの管理操作もゲートウェイ経由で行う。
- 管理者向け境界は一般利用者向け境界と論理的に分離する。

### シミュレーションコア

- 直接依存しない。
- 直接接続しない。
- コアの管理可能操作はゲートウェイを通じて実行する。

### 一般ビュー

- 一般ビューはリードオンリーであり、管理操作を持たない。
- 管理機能を一般ビューへ混在させない。

## 8. 超大規模化における設計要件

- 監視データ取得がシミュレーション計算を大きく阻害しないこと。
- 高頻度な監視表示をコアへの直接問い合わせ連打で実現しないこと。
- 複数ゲートウェイを含む全体状態を把握できる設計とすること。
- 管理操作が通常の参照トラフィックと競合する場合でも影響を制御可能にすること。
- 管理ビュー障害がコアのシミュレーション継続を直接妨げないこと。

## 9. セキュリティ・権限に関する原則

- 管理者向け機能を一般利用者へ公開しない。
- UI 上で非表示にするだけで権限制御を完結させない。
- 最終的な外部境界の権限制御はゲートウェイで実施する。
- コア側でもシミュレーション上の操作妥当性を検証する。
- 重要操作について監査可能性を確保する。

具体的な認証・認可方式は未確定です。

## 10. 禁止する依存・実装

- シミュレーションコアへの直接接続
- コア内部状態の直接書き換え
- ゲートウェイキャッシュの書き換えをコア操作として扱うこと
- UI 上の表示制御だけを認可手段として扱うこと
- 管理画面の都合でシミュレーションルールを変更すること
- 管理ビューを監視データの唯一の保存先にすること

## 11. 今後決定が必要な事項

- 管理者ロールと権限モデル
- 管理操作一覧
- 監視対象メトリクス
- キャッシュ値と正本値の使い分け
- 即時正本確認が必要な管理参照の有無
- ログ閲覧機能
- 監査ログ要件
- アラート機能
- 設定変更可能範囲
- 設定変更の反映方式
- 管理ビューの技術スタック
- 障害対応フロー
- 管理操作の承認フローが必要か
