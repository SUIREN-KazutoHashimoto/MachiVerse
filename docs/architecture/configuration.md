# 外部Config設計

## 1. 目的

MachiVerse では、システム動作を調整する各種数値・設定をソースコードへ運用固定値として埋め込まず、責任コンポーネントが所有する外部Configから供給する。

この方針はSimulation Core、Gateway、General View、Admin Viewの全コンポーネントに適用する。

Configの意味論は本書と `config-semantics.md` を合わせて読む。後続要件Q210〜Q214で確定した内容を、本書の古いTBDより優先する。

## 2. 基本原則

- 調整可能な数値・しきい値・時間・件数・容量・挙動選択等は外部Configから供給する。
- ソースコード内へ運用値・性能調整値・シミュレーション条件を直接固定しない。
- 数学的定数、配列インデックス等、設定値として意味を持たない実装上の数値は対象外とできる。
- 各コンポーネントは、自身が責任を持つ設定を自身のConfigで所有する。
- 他コンポーネントのConfigファイルを直接参照しない。
- コンポーネント間でConfigファイルを共有しない。
- 他コンポーネントへ影響する必要情報は、Coreに近い側の責任コンポーネントが標準プロトコルの契約として配布する。共有Configファイルで伝播しない。
- Configの具体的なファイル形式、配置方式、読み込みライブラリは現時点では未確定とする。

## 3. 現時点で確定している基準値

### 3.1 Simulation Core

- シミュレーション計算頻度の標準値は **30Hz**。
- 権威ある時間軸は整数ベースのSimulation Stepであり、30Hzはその進行に対する標準設定である。
- 30HzはCoreの外部Configから変更可能とする。
- Coreはマルチスレッド実行を前提とし、使用可能スレッド数は **1〜16**。
- 実使用スレッド数はCoreの外部Configから変更可能とする。

### 3.2 Gateway

- 外部公開の揺らぎを吸収する論理的な遅延バッファの標準値は **約1秒**。
- この値はGatewayの外部Configから変更可能とする。
- この遅延バッファはcacheとは別責務であり、OperationやAdmin操作を一律1秒遅らせる意味ではない。

## 4. Configの所有責任

各設定値は、その値を使用して動作を決定する責任コンポーネントが所有する。

| 設定例 | 所有コンポーネント |
|---|---|
| Simulation Step進行頻度 | Simulation Core |
| Core使用スレッド数 | Simulation Core |
| シミュレーション詳細度・世界生成条件 | 原則Simulation Core |
| Gateway公開遅延バッファ | Gateway |
| Gateway cache関連値 | Gateway |
| Gateway timeout・retry・流量制御 | Gateway |
| General View表示更新・表示のみの調整値 | General View |
| Admin View表示・監視UIの調整値 | Admin View |

この表は網羅ではない。所有責任は「どのコンポーネントがその設定により自身の動作を決めるか」で判断する。

## 5. Configの分類

各Config項目は少なくとも次の観点で分類可能にする。

### 5.1 世界結果への影響

- **シミュレーション影響Config**: 世界状態、World Time上の因果、Operation結果、乱数結果、詳細度等へ影響する。
- **表示・運用のみのConfig**: 世界結果へ影響せず、表示や運用・監視だけを変更する。

シミュレーション影響Configは決定論・保存・リプレイの再現条件に含める。

### 5.2 変更可能性

項目ごとに、少なくとも次のような変更可能性を明示する。

- 実行中変更可能
- 再起動が必要
- 世界再生成が必要
- その他、明示的な安全境界が必要

すべてのConfigを同じ変更タイミングで扱わない。

## 6. 起動時検証

- Configは型、範囲、相互制約、依存関係等を検証する。
- **起動時Configに不整合がある場合、その不整合を抱えたままコンポーネントまたは世界を起動しない。**
- 無効値を黙って丸める、無関係な既定値へ置換して起動する等を一般原則としない。
- ただし、後方互換のため「古いConfigに新規項目が存在しない」場合はQ214の規則を適用する。

## 7. 実行中変更

- 実行中変更を許可する項目は、明示的な安全境界で変更セットを原子的に適用する。
- 相互に関連する変更セットの一部だけを適用して中間不整合状態にしない。
- 実行中変更が検証に失敗した場合、変更セットを拒否し、以前の有効Configを維持する。
- シミュレーション影響Configの変更は、明示的なSimulation Step / World Timeと結び付ける。
- シミュレーション影響Config変更は履歴に記録し、保存・リプレイ・障害復旧で同じ因果系列を再現できるようにする。
- Admin ViewからConfigを変更する場合も、一般Undoは行わず、元へ戻す場合は新しい変更Operationとして実行する。

## 8. Configの後方互換性

Q214により、Configには下位互換性を持たせる。

- Configのバージョンが古く、現在のバージョンで追加された項目が欠けている場合、その項目の既定値を有効値として使用する。
- 使用した既定値は、**欠けていた項目としてConfigファイルへ追加する。**
- 単純な「新規項目欠落」と、意味変更・型変更・互換不能な構造変更は区別する。
- 互換不能な変更のmigration規則は、具体的なConfig versioning設計で定義する。未定義の不整合を黙って読み飛ばさない。

## 9. コンポーネント間に影響する設定

Q213により、他コンポーネントへ影響するからといって共通Configファイルを作らない。

例えばCoreが定義するSimulation Stepの意味や、接続相手が知る必要のある有効設定状態は、必要な範囲をCore所有のプロトコル契約としてGatewayへ伝える。GatewayはCoreのConfigファイルを直接読む必要も権限も持たない。

同様に、各プロトコル境界で必要な設定・状態は、よりCoreに近いプロトコル所有側が必要な情報を公開する。

## 10. 数値Configの代表例

- 実行頻度
- 使用スレッド数
- 時間間隔
- 遅延時間
- timeout
- cache保持時間
- buffer量
- 件数上限・size上限
- retry回数・間隔
- 流量制御値
- 詳細度のしきい値・更新頻度
- 保存間隔・保持量
- 監視間隔・保持期間
- その他、運用・性能・シミュレーション挙動を調整する値
