# ゲートウェイ設計

## 1. 目的

ゲートウェイは、シミュレーションコアと外部利用者・外部画面・管理機能の間に位置する接続境界です。

MachiVerse は超大規模利用を前提とするため、ゲートウェイは特定の単一プロセスや単一ノードへ固定されず、将来的にスケールアウトできる構造を取れることを前提とします。

## 2. 主な責務

ゲートウェイは、少なくとも以下の機能責務を持ちます。

- 外部からの要求受付
- 一般利用者向け要求と管理者向け要求の論理的分離
- 外部要求の形式検証
- シミュレーションコアへの要求仲介
- シミュレーション状態の外部配信
- 外部クライアント接続の管理
- 認証・認可を配置するための境界提供
- 負荷分散・スケールアウトを可能にする構造
- 通信上のエラー処理
- 外部公開モデルへの変換
- 必要に応じた流量制御

## 3. 責務外

以下はゲートウェイの直接責務としません。

- シミュレーションルールそのものの決定
- エージェントの内部状態遷移ロジック
- シミュレーション時間の進行
- UI の描画
- 管理画面の描画
- シミュレーション状態の正本管理
- 表示専用の画面状態管理

## 4. 主要機能

### 4.1 要求受付

ビュー、管理ビュー、その他将来的な外部クライアントから要求を受け付けます。

通信プロトコル、エンドポイント形式、接続方式は現時点では未確定です。

### 4.2 要求検証

外部から受け取った要求について、少なくとも通信境界として検証可能な事項を確認します。

例として、形式、必須項目、サイズ、権限などが考えられます。シミュレーション上の意味的な妥当性は、最終的にシミュレーションコア側の責務とします。

### 4.3 要求仲介

外部形式で受け取った要求を、シミュレーションコアが扱える境界へ変換・仲介します。

ゲートウェイがシミュレーション内部ルールを再実装しないことを原則とします。

### 4.4 状態配信

シミュレーションコアから参照可能な情報を取得し、外部クライアントへ配信します。

利用者数や更新頻度が増加した際に、同一情報取得がコアへ過剰な負荷を与えない構成を検討できるようにします。

### 4.5 接続管理

外部クライアントとの接続状態を管理します。

長時間接続、短時間要求、ストリーム配信など、具体的な接続モデルは今後決定します。

### 4.6 認証・認可境界

一般利用者と管理者で許可される操作が異なるため、ゲートウェイは権限制御を配置できる境界を提供します。

具体的な認証方式、認可モデル、ID 管理方式は未確定です。

### 4.7 スケールアウト

ゲートウェイは複数インスタンスへ拡張可能な構造を目標とします。

以下は設計時に検討対象となります。

- セッション状態をどこに持つか
- インスタンス間で共有が必要な情報は何か
- 接続先インスタンスが変わっても継続可能か
- 同一要求の重複処理をどう扱うか
- 配信対象の振り分けをどう行うか
- 一部インスタンス障害時に他インスタンスへ切り替えられるか

ただし、具体的な製品・技術・分散方式は現時点では確定しません。

### 4.8 流量制御

ビュー側の要求量がシミュレーションコアの処理能力を上回る場合に備え、要求数や配信量を制御できる境界を持たせます。

レート制限、バックプレッシャー、キューイングなどの採否は今後決定します。

### 4.9 外部公開モデル変換

シミュレーションコア内部のデータ構造をそのまま外部へ公開せず、外部公開用のモデルへ変換する責務を持たせます。

これにより、コア内部構造の変更が外部 API へ直接波及することを防ぎます。

## 5. データ所有権

ゲートウェイが保持するデータは、原則として接続・転送・公開・キャッシュ等の目的に限定します。

シミュレーション状態の正本はシミュレーションコア側にあります。ゲートウェイにキャッシュを設ける場合、その内容は正本ではなく、失効条件を明確にする必要があります。

## 6. 他領域との関係

### シミュレーションコアとの関係

- 外部操作をコアへ仲介する。
- コアから外部公開可能な状態を取得する。
- コア内部の可変データ構造を直接操作しない。

### ビューとの関係

- ビューからの一般利用者向け要求を受け付ける。
- ビューへ外部公開用データを返す。
- ビュー固有の描画ロジックは持たない。

### 管理ビューとの関係

- 管理者向け要求を受け付ける。
- 管理情報を返す。
- 一般利用者向け境界と管理者向け境界を論理的に区別する。

## 7. 超大規模化における設計要件

- 水平スケールを阻害するローカル状態依存を最小化する。
- 接続数の増加とシミュレーション負荷を分離できること。
- 外部要求量が増加してもコアを無制限に呼び出さないこと。
- 一部ノード障害を全体停止へ波及させにくいこと。
- 要求数、処理時間、エラー、接続数などを観測可能にすること。
- 一般利用者向け負荷と管理向け負荷を識別できること。

## 8. 禁止する依存・実装

- シミュレーションルールをゲートウェイ内へ複製すること
- コア内部の可変状態を直接書き換えること
- ビュー固有の UI ロジックを持つこと
- 管理ビュー固有の UI ロジックを持つこと
- 単一インスタンスのメモリ状態だけを前提とした設計を、スケーラブル要件確認なしに固定すること

## 9. 今後決定が必要な事項

- 通信プロトコル
- API 形式
- ストリーム配信の有無
- 接続モデル
- 認証方式
- 認可モデル
- セッション管理方式
- キャッシュ方式
- 負荷分散方式
- インスタンス間連携方式
- 流量制御方式
- 再試行方針
- 冪等性要件
- API バージョニング
- 外部公開モデル
- 可観測性方式
