# ゲートウェイ設計

## 1. 目的

本書は、MachiVerse におけるゲートウェイの責務、シミュレーションコアとの関係、マスターゲートウェイ、参照キャッシュ、操作集約、複数コア間のProxy参照、および利用者接続のハンドオーバーに関する現時点の設計を定義します。

ゲートウェイは、シミュレーションコアと一般ビュー・管理ビューの間に位置する接続・認可・緩衝・調停境界です。一般ビューおよび管理ビューはシミュレーションコアへ直接接続しません。

ゲートウェイはシミュレーション状態の正本ではありません。正本は各シミュレーションコアが保持し、ゲートウェイは外部参照用のキャッシュと遅延バッファを持つことで、コアをシミュレーション計算へ専念させます。

## 2. 基本原則

1. シミュレーションコアとゲートウェイは1対多とする。
2. 各シミュレーションコアには必ず少なくとも1つのゲートウェイを用意する。
3. 1つのコアに複数ゲートウェイが存在する場合、コアがその中からマスターゲートウェイをランダムに選出する。
4. 一般ビュー由来のコアへの干渉要求は、各ゲートウェイで認証・認可・ローカル集約・ローカル競合調停を行った後、マスターゲートウェイへ集約する。
5. マスターゲートウェイは担当コア配下のゲートウェイから集めた要求をさらに集約・競合調停し、コアへ最終操作バッチとして一括要求する。
6. 外部参照要求は可能な限りゲートウェイのキャッシュから処理し、コアへの参照負荷を抑える。
7. 複数コア構成では、現在のゲートウェイ担当範囲外の情報は、現在側のマスターゲートウェイが別コア側ゲートウェイへProxyして取得できる。
8. 利用者の接続先は固定的な地理境界だけで決定せず、ゲートウェイ負荷と利用者が必要とするデータの取得範囲割合を基準にハンドオーバーできる。
9. 利用者にコア境界やゲートウェイ境界を必要以上に意識させず、一つの連続した世界として扱えることを優先する。
10. ゲートウェイはシミュレーションルールを複製せず、世界状態・ルールに基づく最終妥当性判断はコアに委ねる。

## 3. コンポーネント境界

ゲートウェイは他コンポーネントとコード、DLL、内部型、共有DTOライブラリを通信契約として共有しません。コンポーネント間通信はプロトコルだけを介して行います。

| 境界 | プロトコル所有者 | 設計書 |
|---|---|---|
| シミュレーションコア ↔ ゲートウェイ | シミュレーションコア | `docs/protocols/core-gateway.md` |
| ゲートウェイ ↔ ゲートウェイ | ゲートウェイ | `docs/protocols/gateway-gateway.md` |
| ゲートウェイ ↔ 一般ビュー | ゲートウェイ | `docs/protocols/gateway-view.md` |
| ゲートウェイ ↔ 管理ビュー | ゲートウェイ | `docs/protocols/gateway-admin-view.md` |

複数コア構成での別コア側ゲートウェイへのProxy参照および利用者ハンドオーバーも、ゲートウェイ間プロトコルを契約として実施します。

## 4. 主な責務

ゲートウェイは以下を担当します。

- 一般ビュー・管理ビューからの要求受付
- 一般ビュー利用者の認証・ロール認可
- ロールに応じた参照情報の制御
- 外部クライアント接続管理
- シミュレーション状態の参照用キャッシュ
- 約1秒分を基準とする遅延バッファ管理
- 一般ビュー由来操作のローカル集約
- 同一ゲートウェイ内の外部要求レベル競合調停
- ローカル操作バッチ形成
- 非マスター時のマスターゲートウェイへの操作バッチ転送
- マスター時の担当コア配下ゲートウェイの操作バッチ集約
- マスター時のゲートウェイ間外部要求レベル競合調停
- マスター時のコア向け最終操作バッチ形成・一括送信
- コアから返された操作結果の元ゲートウェイへの振り分け
- コアによるマスター選出・変更通知の受理
- 担当範囲外データのProxy取得
- 利用者接続先ゲートウェイのハンドオーバー調整
- 負荷分散・水平スケール
- 通信エラー処理・流量制御
- 管理ビューからの運用・設定・コマンド要求の仲介

## 5. 責務外

ゲートウェイは以下を正本責務として持ちません。

- シミュレーションルールそのものの決定
- エージェント内部状態遷移ロジック
- シミュレーション時間の進行
- シミュレーション状態の正本管理
- 世界状態・シミュレーションルール上の最終操作妥当性判断
- マスターゲートウェイの選出決定
- シミュレーションコア間のリング構成およびコア間シミュレーション連携そのもの
- シミュレーションコア・ゲートウェイ間プロトコルの所有

## 6. 単一コア内のゲートウェイ構成

1つのシミュレーションコアに複数のゲートウェイを接続できます。

```text
一般ビュー群 ──> Gateway A ─┐
                             │ local batch
一般ビュー群 ──> Gateway B ─┼──> Master Gateway ── final batch ──> Simulation Core
                             │
一般ビュー群 ──> Gateway C ─┘
```

各ゲートウェイは通常の利用者接続、参照配信、ローカル操作集約を担当できます。マスターゲートウェイも通常のゲートウェイとして利用者を受け持てます。

マスター役割は、担当コアへ向かう一般ビュー由来の書き込み経路を集約するための役割であり、通常の参照要求をすべてマスターへ集中させるものではありません。

## 7. マスターゲートウェイ

### 7.1 選出

マスターゲートウェイの選出責任はシミュレーションコアが持ちます。

- 選出対象は、その時点でコアが有効な接続先として認識しているゲートウェイとする。
- 選出方式はランダムとする。
- 選出結果を対象ゲートウェイ群へ通知する。
- マスターが停止・切断・利用不能になった場合、コアが新しいマスターを再選出する。
- マスターは恒久的な固定ノードではなく役割として扱う。

ランダム選出に使用する具体的な乱数方式、重み付け、直前マスターの再選出可否は未確定です。

### 7.2 書き込み集約

一般ビュー由来操作は以下の経路で処理します。

```text
一般ビュー
   ↓
接続先Gateway
   ↓ 認証・認可
ローカル操作集約
   ↓
ローカル競合調停
   ↓ local batch
Master Gateway
   ↓ 担当Core配下のGateway分を集約
Gateway間競合調停
   ↓ final batch
Simulation Core
   ↓
世界状態・ルール上の最終妥当性判定
   ↓
正本状態へ反映
```

非マスターゲートウェイは、一般ビュー由来のローカル操作バッチを担当コアへ直接送信しません。

### 7.3 競合調停の責務階層

競合調停は3段階に分けます。

1. **ローカル競合調停**: 各ゲートウェイが、自身へ到達した外部要求同士を整理する。
2. **ゲートウェイ間競合調停**: マスターゲートウェイが、担当コア配下のゲートウェイから集めた操作バッチ間の外部要求レベル競合を整理する。
3. **シミュレーション妥当性判定**: コアが、正本世界状態とシミュレーションルールに基づいて最終実行可否を判断する。

ゲートウェイの競合調停にシミュレーションルールを複製しません。

### 7.4 マスター障害・切替

マスター切替時には、少なくとも以下の重複・欠落を防止する必要があります。

- 旧マスターへ送信済みだがコアへ未送信のバッチ
- 旧マスターがコアへ送信済みだが結果未確定のバッチ
- 新マスターへの再送による二重転送
- 同一操作の二重適用
- 古いマスター世代の遅延メッセージ

そのため、マスター選出世代またはepoch、バッチ識別子、操作識別子、再送・冪等性の契約が必要です。具体的な形式はプロトコル設計で定義します。

## 8. キャッシュ

### 8.1 目的

ゲートウェイキャッシュは、一般ビュー等からの参照要求をコアから切り離し、コアへの高頻度な読み取り負荷を抑えるための参照用複製です。

キャッシュはシミュレーション状態の正本ではありません。正本は常に担当シミュレーションコアにあります。

### 8.2 キャッシュ更新

コアからゲートウェイへの具体的な状態配信方式は未確定です。Push/Pull、全量・差分・スナップショット、更新頻度、無効化方式、同一コア配下ゲートウェイ間の整合性方式は別途定義します。

## 9. 遅延バッファ

ゲートウェイは、コアの計算頻度・状態到着間隔の一時的な揺らぎを外部へ直接露出させないため、基準値として約1秒分の遅延を設けます。

コアの計算頻度の基準値は30Hzであるため、1秒は概念上約30ステップに相当しますが、実装を30件固定のキューに限定するものではありません。

キャッシュと遅延バッファは別の責務です。

- キャッシュ: コアへの参照負荷を分離する。
- 遅延バッファ: 外部へ公開する時間系列の揺らぎを吸収する。

約1秒という値は外部Configから変更可能です。一般ビュー由来操作や管理操作そのものを一律1秒遅延させる要件ではありません。

## 10. 複数コア構成との関係

MachiVerse は複数のシミュレーションコアを用意でき、コアを追加することで詳細にシミュレーションする領域を追加できる構成を採用します。1つのコアが詳細にシミュレーションする担当範囲は固定とします。

コア間通信はリング型とします。ただし、リング構成そのもの、コア間で受け渡すシミュレーション情報、領域境界における状態・エージェント等の扱いはコア側の設計責務であり、本書ではGatewayから見た関係のみ定義します。

各コアには必ず少なくとも1つのゲートウェイを用意します。

概念構成は以下です。

```text
Core A ── Core B ── Core C ── Core D
  ↑          ↑          ↑          ↑
GW群A       GW群B       GW群C       GW群D
  └──────────────────────────────┘
      利用者からは連続した世界として扱う

Core間は論理リングとして接続する。
```

ゲートウェイは利用者に対して「コアを移動する」という操作モデルを要求せず、必要に応じて参照ProxyまたはGatewayハンドオーバーによって担当領域の違いを吸収します。

## 11. 担当範囲外データのProxy参照

### 11.1 基本方針

利用者が現在接続中Gatewayの担当範囲外の情報を必要としただけでは、接続先Gatewayを即座に変更しません。

現在側のマスターゲートウェイがProxyとして別コア側のゲートウェイから必要な情報を取得し、現在の接続経路を通して利用者へ返します。

```text
利用者
  ↓
現在Gateway
  ↓
現在Core側 Master Gateway
  ↓ Proxy
別Core側 Gateway
  ↓
別Core側の参照キャッシュ
```

Proxy参照もコアの正本状態へ直接読み取り要求を集中させるのではなく、原則として別コア側Gatewayが外部参照用に保持する情報を利用します。

### 11.2 Proxyとハンドオーバーの分離

担当範囲外参照が一時的・少量であればProxyを利用し、利用者接続を維持します。

利用者が必要とする情報の中心が別Gateway側へ移った場合は、Proxyを継続し続けるのではなく、接続先Gatewayそのものをハンドオーバーします。

## 12. Gatewayハンドオーバー

### 12.1 判断要素

ハンドオーバー判断には、少なくとも次の2要素を使用します。

1. **Gatewayの負荷状況**
   - 現在Gatewayと移動候補Gatewayの負荷を判断材料とする。
   - CPU使用率等の具体的な負荷指標は現時点では確定しない。

2. **利用者が必要とするデータの取得範囲割合**
   - 現在Gateway側から直接取得するデータと、他GatewayへのProxyによって取得するデータの割合を判断材料とする。
   - 少なくともProxy側から取得するデータの方が多くなる場合は、別Gatewayへのハンドオーバーを行う条件とする。

したがって、地理的な境界線を越えたことだけをハンドオーバー条件とはしません。

### 12.2 ハンドオーバー調整

ハンドオーバーが必要になった場合、現在側のマスターゲートウェイが移行をハンドリングし、利用者をより適切な別ゲートウェイへ移します。

利用者からは、一つの世界を移動・参照している途中でインフラ上の接続先が変化したものとして扱い、「別コアへ接続し直す」という操作を要求しない方向とします。

### 12.3 スラッシング防止

境界付近や取得範囲割合が拮抗する状況で、Gateway AとGateway Bの間を短時間に往復し続ける状態は避ける必要があります。

スラッシング防止機構は必要としますが、ヒステリシス、最低滞在時間、評価期間等の具体方式は未確定です。調整可能な数値を使用する場合はGatewayの外部Configから変更可能にします。

### 12.4 ハンドオーバー時の未確定事項

以下は別途プロトコル設計で確定します。

- セッション状態の引き継ぎ
- 認証・認可状態の引き継ぎまたは再検証
- 未完了操作の扱い
- 操作結果の返却先
- 一時的な重複接続の可否
- 切断・切替タイミング
- 重複・欠落防止
- ハンドオーバー失敗時の復旧

## 13. 一般ビュー利用者ロールと認可

一般ビューには以下の利用者ロールがあります。

| ロール | シミュレーションへの干渉 | 参照範囲 |
|---|---|---|
| ダイバー | シミュレーション住民と同程度 | 参加者として許可された情報 |
| スペクテイター | 不可 | システムのバイタルに関係しない程度のステータス |
| モデレーター | シミュレーションおよび下位利用者へ限定的に可能。クリティカル操作は禁止 | スペクテイターと同等 |
| アドミニストレーター | シミュレーションへ完全に干渉可能 | 一般ビュー向け全ステータス |

GatewayはUI上の表示・非表示だけに認可を依存せず、各要求をGateway側で検証します。

- スペクテイターの状態変更要求はコアへ到達させない。
- モデレーターのクリティカルな要求はコアへ到達させない。
- 下位利用者への操作ではロール階層を検証する。
- Gatewayで認可された操作であっても、世界状態・ルール上の理由によりコアが拒否できる。

一般ビューのアドミニストレーターと管理ビューの運用権限は別概念です。

## 14. 管理ビュー要求

管理ビューは一般ビューの最上位ロールではなく、コンポーネント運用のための別境界です。

管理ビューでは各コンポーネントのログ、稼働・診断状態、外部Config、運用コマンド、シミュレーションへの運用上の干渉を扱います。

管理ビュー由来のコア干渉要求をマスターゲートウェイ経由へ統一するか、別の管理経路を持つかは未確定です。

## 15. スケールアウト

Gatewayは水平スケール可能とします。1つのコアに複数Gatewayを配置することで、利用者接続・参照配信等の外部負荷を分散できます。

担当コア内ではマスターゲートウェイ1台が一般ビュー由来の書き込み集約点になるため、Gateway数・操作量が増大した場合はボトルネックになり得ます。現時点では1コアにつきマスター1台方式とし、将来の分割方式は実測上必要になった場合に別途設計します。

複数コア構成では、コア追加による詳細シミュレーション領域の追加と、各コア配下Gateway群による利用者・参照負荷の分散を組み合わせます。

## 16. 決定性との関係

Gatewayの存在数、どのGatewayがマスターになったか、処理速度、通信到着競争等の運用上の差異によって、同一Seed・同一シミュレーション設定・同一操作から得られるシミュレーション結果を変えてはなりません。

そのため、操作集約・競合調停・再送・重複排除・ハンドオーバー等を設計する際は、到着タイミングやスレッド実行順だけで結果が変化する方式を避け、シミュレーションへ渡される有効操作を決定的に扱える必要があります。

具体的な決定順序規則は未確定です。

## 17. 外部Config

Gatewayの運用・性能・挙動を調整する数値は、原則としてGatewayが所有する外部Configから変更可能にします。

対象例には以下を含みます。

- 遅延バッファ時間
- キャッシュ関連の時間・件数・サイズ上限
- タイムアウト
- 再試行回数・間隔
- 接続数上限
- 流量制御値
- 操作集約に関する時間・件数・サイズ
- マスター生存判定・切替に関する調整値
- Proxy参照に関する調整値
- ハンドオーバー評価に関する調整値
- スラッシング防止に関する調整値

具体的なConfigキー、既定値、動的再読込可否は未確定です。

## 18. プロトコルバージョニング

Gatewayが所有または利用する各コンポーネント間プロトコルは、既存の共通方針に従い `Major.Minor` の概念を持ちます。

- Majorが一致する場合のみ接続を許可する。
- Majorが異なる場合は接続を拒否する。
- 同一Major内では異なるMinor間の接続を許可する。
- 新しいMinorは同一Majorの古いMinorとの後方互換性を維持する。
- 後方互換性を維持できない変更はMajor更新とする。

## 19. 禁止事項

- 一般ビュー・管理ビューからコアへ直接接続すること
- 非マスターGatewayが一般ビュー由来のローカル操作バッチを担当コアへ直接送信すること
- 複数Gatewayが同時に同一コアのマスターとして通常の最終操作バッチを書き込むこと
- Gateway側でシミュレーションルールを複製すること
- Gatewayキャッシュをシミュレーション状態の正本として扱うこと
- マスター選出をGateway同士の暗黙合意だけで決定すること
- マスター切替時に識別情報なしで操作を再送すること
- 一般ビューのアドミニストレーターへ管理ビュー専用権限を自動付与すること
- 担当範囲外データを参照しただけで、負荷状況や取得範囲割合を考慮せず常に即時ハンドオーバーすること
- GatewayやMasterの処理タイミング差をシミュレーション結果を変える暗黙入力として扱うこと

## 20. 現時点で確定している事項

- Core : Gateway は1対多。
- 各Coreには少なくとも1つのGatewayを用意する。
- Gatewayは水平スケール可能。
- 複数Gateway時はCoreがMaster Gatewayをランダムに選出する。
- 一般ビュー由来操作は各Gatewayでローカル集約・競合調停する。
- 非Master Gatewayはローカル操作バッチをMaster Gatewayへ送る。
- Master Gatewayは担当Core配下のバッチを集約・競合調停し、Coreへ一括要求する。
- Coreが正本世界状態とシミュレーションルール上の最終妥当性を判断する。
- Gatewayは参照用キャッシュを持つ。
- Gatewayは約1秒を基準とする遅延バッファを持つ。
- 複数Coreを用意でき、Core追加によって詳細シミュレーション領域を追加できる。
- 1 Coreが詳細にシミュレーションする担当範囲は固定。
- Core間通信はリング型。
- 担当範囲外参照は現在側Master Gatewayが別Core側GatewayへProxyできる。
- Gatewayハンドオーバー判断には負荷状況とデータ取得範囲割合を使用する。
- 少なくともProxy取得側のデータ割合が直接取得側を上回る場合は別Gatewayへハンドオーバーする。
- ハンドオーバーは現在側Master Gatewayが調整する。
- 調整可能な数値は外部Config化する。
