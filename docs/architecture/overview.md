# 全体アーキテクチャ

## 1. 目的

本書は、MachiVerse の最上位アーキテクチャを定義します。対象読者は、本システムに初めて参加する開発者、運用担当者、レビュー担当者です。

MachiVerse は、C# で開発する超大規模エージェントベースシミュレーションです。規模拡大に伴って責務が混在すると、性能問題、変更影響範囲の肥大化、並列化・分散化の困難化、障害範囲の拡大を招くため、最上位の責務境界を明確に分離します。

## 2. 最上位コンポーネント

システムは以下の4領域で構成します。

| 領域 | 主目的 | 主な責務 |
|---|---|---|
| シミュレーションコア | シミュレーションの実行 | 状態保持、時間進行、エージェント・環境の状態遷移、シミュレーションルールの実行 |
| ゲートウェイ | 外部との接続境界 | コアとの仲介、状態キャッシュ、データ配信、管理要求の中継、スケーラブルな接続処理 |
| ビュー | 一般利用者向け閲覧 | ゲートウェイから取得したシミュレーション状態の読み取り専用表示 |
| 管理ビュー | 運用・管理 | システム監視、管理情報の表示、ゲートウェイ経由でのコア管理操作 |

## 3. 基本構成と多重度

シミュレーションコアとゲートウェイは 1 対多の関係とします。

```text
                         ┌─> ゲートウェイ A ──> 一般ビュー群
                         │                 └──> 管理ビュー群
シミュレーションコア ───┼─> ゲートウェイ B ──> 一般ビュー群
                         │                 └──> 管理ビュー群
                         └─> ゲートウェイ N ──> 一般ビュー群
                                           └──> 管理ビュー群
```

1つのシミュレーションコアに対して複数のゲートウェイを配置できる構成を前提とします。ゲートウェイは水平スケール可能な外部境界として扱い、利用者数や参照要求数の増加をコアへ直接集中させない役割を持ちます。

## 4. 依存方向

依存方向は次の通りです。

```text
一般ビュー ──(読み取りのみ)──> ゲートウェイ ──(参照/管理要求)──> シミュレーションコア
管理ビュー ──(参照/管理操作)─> ゲートウェイ ──(管理要求)──────> シミュレーションコア
```

一般ビューおよび管理ビューは、シミュレーションコアへ直接アクセスしません。

シミュレーションコアは、ビューや管理ビューの存在を前提とせず、UI の都合、画面更新頻度、接続クライアント数などをシミュレーションロジックへ持ち込みません。

## 5. 読み取りと書き込みの境界

### 5.1 一般ビュー

一般ビューはリードオンリーです。

一般ビューはゲートウェイから公開済みのシミュレーション情報を取得して表示します。一般ビューからシミュレーション状態を変更する要求は送信しません。

### 5.2 管理ビュー

管理ビューはゲートウェイを通じてシミュレーションコアへ管理操作を要求できます。

管理ビュー自身がコア状態を直接変更することはなく、すべての管理操作はゲートウェイを経由します。ゲートウェイは認証・認可、形式検証、管理境界としての制御を行い、シミュレーション上の最終的な整合性判断と状態変更はコア側が担当します。

## 6. ゲートウェイキャッシュ

ゲートウェイは、シミュレーション状態の外部参照用データをキャッシュします。

主目的は、一般ビューや管理ビューからの高頻度な参照要求をシミュレーションコアへ直接到達させず、コアをシミュレーション計算へ専念させることです。

原則は次の通りです。

- シミュレーション状態の正本はコアが保持する。
- ゲートウェイのキャッシュは参照用の複製であり、正本ではない。
- 一般ビューの読み取り要求は、可能な限りゲートウェイキャッシュから応答する。
- 管理ビューの参照要求も、即時の正本確認が必要でないものはキャッシュから応答できる。
- キャッシュ更新方式、失効方式、整合性保証レベルは別途定義する。
- ゲートウェイ台数の増加によって、コアへの参照負荷が同じ比率で増大しない設計とする。

## 7. 主要なデータフロー

### 7.1 一般利用者が状態を見る場合

1. 一般ビューがゲートウェイへ参照要求を送る。
2. ゲートウェイがキャッシュから公開可能な状態を取得する。
3. ゲートウェイが一般ビューへ応答する。
4. 一般ビューが受け取った情報を表示する。

通常の参照処理では、一般ビューからの要求ごとにシミュレーションコアへ問い合わせないことを基本とします。

### 7.2 ゲートウェイが状態を更新する場合

1. シミュレーションコアが外部公開可能な状態を提供する。
2. ゲートウェイがその状態を受け取り、各自のキャッシュを更新する。
3. 一般ビューおよび管理ビューへの後続参照は、そのキャッシュを利用する。

具体的な更新方式が Push、Pull、差分配信、スナップショット等のどれになるかは未確定です。

### 7.3 管理者がコアへ管理操作を行う場合

1. 管理ビューがゲートウェイへ管理要求を送る。
2. ゲートウェイが管理要求として認証・認可・形式検証を行う。
3. ゲートウェイがシミュレーションコアへ管理要求を伝達する。
4. シミュレーションコアがシミュレーション上の妥当性を判断し、必要な状態変更を行う。
5. 必要に応じて結果をゲートウェイ経由で管理ビューへ返す。
6. 状態変更後の外部公開状態は、通常のキャッシュ更新経路で各ゲートウェイへ反映する。

## 8. 責務分離の原則

### 8.1 データ所有権

シミュレーション状態の正本はシミュレーションコアが所有します。ゲートウェイおよび各ビューが保持する情報は正本として扱いません。

### 8.2 更新権限

一般ビューにはシミュレーション状態の更新権限を与えません。管理ビューからの更新要求は必ずゲートウェイを経由し、最終的な状態変更はコア自身が実行します。

### 8.3 内部実装の隠蔽

ある領域が別領域の内部データ構造、内部クラス、内部ストレージ構造を直接操作しません。

### 8.4 外部都合の隔離

通信方式、画面構成、利用者数、運用ツールなどの都合を、シミュレーションロジックそのものから隔離します。

## 9. 障害境界

- 一般ビューの障害がシミュレーション実行を停止させない。
- 管理ビューの障害がシミュレーション実行や通常閲覧を直接停止させない。
- 一部ゲートウェイの障害が全クライアント停止へ直結しない構成を可能にする。
- ゲートウェイ障害時にもコアは可能な限りシミュレーション計算を継続できるようにする。
- コアの内部障害は、ゲートウェイを経由して管理側から観測・診断可能にする。

## 10. 現時点で確定している事項

- C# を用いる。
- 超大規模エージェントベースシミュレーションである。
- 最上位領域は「シミュレーションコア」「ゲートウェイ」「ビュー」「管理ビュー」の4つとする。
- シミュレーションコアとゲートウェイは 1 対多の関係とする。
- ゲートウェイは水平スケール可能な構成を前提とする。
- ゲートウェイは参照用状態をキャッシュし、コアへの参照負荷を抑える。
- 一般ビューはリードオンリーとする。
- 一般ビューはゲートウェイにのみアクセスする。
- 管理ビューもゲートウェイにのみアクセスする。
- コアへの管理操作は、管理ビューからゲートウェイを経由して行う。
- シミュレーション状態の正本はコアが保持する。
- ドキュメントは日本語を基準とする。
