# 全体アーキテクチャ

## 1. 目的

本書は、MachiVerse の最上位アーキテクチャを定義します。対象読者は、本システムに初めて参加する開発者、運用担当者、レビュー担当者です。

MachiVerse は、C# で開発する超大規模エージェントベースシミュレーションです。規模拡大に伴って責務が混在すると、性能問題、変更影響範囲の肥大化、並列化・分散化の困難化、障害範囲の拡大を招くため、最上位の責務境界を明確に分離します。

## 2. 最上位コンポーネント

システムは以下の4領域で構成します。

| 領域 | 主目的 | 主な責務 |
|---|---|---|
| シミュレーションコア | シミュレーションの実行 | 状態保持、時間進行、エージェント・環境の状態遷移、シミュレーションルールの実行 |
| ゲートウェイ | 外部との接続境界 | 外部要求の受付、コアとの仲介、データ配信、スケーラブルな接続処理 |
| ビュー | 一般利用者向け表示・操作 | シミュレーション状態の表示、利用者操作の受付、表示用状態の管理 |
| 管理ビュー | 運用・管理 | システム監視、運用操作、管理情報の表示、管理者向け操作 |

## 3. 基本的な依存方向

基本的な依存関係は次の向きとします。

```text
ビュー ───────┐
               ├─> ゲートウェイ ─> シミュレーションコア
管理ビュー ───┘
```

ビューおよび管理ビューは、シミュレーションコアへ直接アクセスしません。外部からコアへ到達する要求は、原則としてゲートウェイを境界として扱います。

シミュレーションコアは、ビューや管理ビューの存在を前提としません。UI の都合や表示形式、画面更新頻度などをシミュレーションロジックへ持ち込まないことを基本原則とします。

## 4. 責務分離の原則

### 4.1 データ所有権

各データについて、どの領域が正本を保持するかを明確にします。同一の業務上の状態を複数領域が独立して正本として管理しないようにします。

### 4.2 更新権限

正本データを変更できる領域を限定します。別領域が変更を要求する場合は、定義された境界を通じて要求します。

### 4.3 内部実装の隠蔽

ある領域が、別領域の内部データ構造、内部クラス、内部ストレージ構造を直接操作することを避けます。

### 4.4 外部都合の隔離

通信方式、画面構成、利用者数、運用ツールなどの都合が、シミュレーションロジックそのものへ侵入しないようにします。

### 4.5 スケーラビリティ

ゲートウェイはスケールアウト可能な構成を前提に設計します。ただし、具体的な分散方式、ロードバランシング方式、メッセージング方式、キャッシュ方式などは現時点では未確定です。

## 5. 主要なデータの流れ

### 5.1 一般利用者が状態を見る場合

1. ビューが利用者操作または表示更新を起点としてデータを要求する。
2. ゲートウェイが要求を受け付ける。
3. 必要に応じてゲートウェイがシミュレーションコアから情報を取得する。
4. ゲートウェイが外部向けに適切な形へ仲介する。
5. ビューが受け取った情報を表示する。

### 5.2 一般利用者が操作を行う場合

1. ビューが利用者操作を受け付ける。
2. ゲートウェイへ操作要求を送る。
3. ゲートウェイが要求の妥当性を確認し、必要な処理をコアへ渡す。
4. シミュレーションコアが、自身のルールに従って状態変更を行う。
5. 結果が必要であればゲートウェイを経由してビューへ返す。

### 5.3 管理者が運用操作を行う場合

1. 管理ビューが管理者操作を受け付ける。
2. ゲートウェイ上の管理向け境界へ要求する。
3. ゲートウェイが管理要求として処理し、必要に応じてコアまたは他の管理対象へ伝達する。
4. 管理ビューへ結果を返す。

通常利用者向け操作と管理者向け操作は、権限と影響範囲が異なるため、論理的に分離して扱います。

## 6. 障害境界

超大規模システムでは、1領域の障害をシステム全体へ無制限に波及させないことが重要です。

現時点では具体的な耐障害方式は未確定ですが、少なくとも以下を設計上の目標とします。

- ビューの障害がシミュレーション実行そのものを停止させない。
- 管理ビューの障害が通常利用者向け機能を直接停止させない。
- 一部ゲートウェイの障害が全接続停止へ直結しない構成を検討可能にする。
- シミュレーションコアの内部障害は、外部層から観測・診断可能にする。

## 7. 性能と拡張性に関する考え方

MachiVerse は超大規模シミュレーションを前提とするため、各領域の設計では以下を意識します。

- 処理量の増加に対してボトルネックの所在を特定できること。
- 領域単位でスケール戦略を変更できること。
- 表示要求の増加がシミュレーション計算を不必要に圧迫しないこと。
- 管理機能が通常処理へ過度な負荷を与えないこと。
- 将来的な並列化・分散化を阻害する直接参照や共有可変状態を増やさないこと。

## 8. 現時点で確定している事項

- C# を用いる。
- 超大規模エージェントベースシミュレーションである。
- 最上位領域は「シミュレーションコア」「ゲートウェイ」「ビュー」「管理ビュー」の4つとする。
- ゲートウェイはスケーラブルな構成を前提とする。
- ドキュメントは日本語を基準とする。
