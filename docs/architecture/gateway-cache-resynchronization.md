# Gateway再接続・キャッシュ再同期設計

## 確定方針

第225〜229問はすべてCを採用する。第229については、Gatewayが再同期中である場合、その状態を利用者へ通知することを必須要件とする。

### 非Master Gateway切断時

- 非Master Gatewayの切断によって、未確認の外部Operationを単純に消失させない。
- 未確認Operationを再送可能な形で保持する。
- 再接続先やMaster Gateway、Master世代が変化していても、同じ論理操作についてOperation IDを維持する。
- 再送・再接続・Master切替が発生してもEnd-to-Endの重複排除によって世界へ同一Operationを複数回作用させない。

### Gateway再接続時の状態同期

- 再接続後に切断前のキャッシュを無検証で正規配信へ使用しない。
- Coreまたはプロトコル上の正規な同期元から必要な状態または差分を取得する。
- Gatewayが保持するキャッシュについて、基準World Time、世代その他必要な同期識別情報を検証可能にする。
- 不整合または不足を検出した場合は必要範囲を再同期し、整合性が確認されてから正規配信へ復帰する。
- 差分同期、全量同期、同期元選択等の具体方式は現時点では固定しない。

### Gatewayキャッシュの権威性

- 世界状態の唯一の権威はSimulation Coreとする。
- Gatewayキャッシュは非権威の派生状態であり、Coreと同格の世界状態として扱わない。
- Gatewayキャッシュの不整合を検出し、必要に応じて破棄・再取得・再構築できることを標準要件とする。
- Gatewayキャッシュの消失や破損がSimulation Coreの世界状態消失を意味しない設計とする。

### 公開遅延バッファ

- Gatewayが持つ約1秒の公開遅延は単純な固定sleepとして定義しない。
- Coreから受け取った状態を一定のWorld Time幅に相当する範囲で保持し、ネットワークジッタ吸収や配信順序安定化に利用する論理バッファとして扱う。
- バッファ長その他調整可能な数値は外部Configで設定可能とする。
- 公開遅延バッファとGatewayの状態キャッシュは概念上別の責務とする。実装上のデータ共有方法は現時点では固定しない。
- 30HzのCore計算基準は、General View等へ30Hzで必ず公開することを意味しない。

### バッファ不足・大幅遅延・再同期

- 欠落、順序不整合、同期基準の不一致等を検出した場合、必要な状態または差分を再取得する。
- 不整合な状態列を正常な世界状態であるかのようにGeneral View等へ配信しない。
- 再同期中の公開方法はプロトコル上で明示可能にする。公開停止、最後に整合していた状態の継続表示等の具体方針は今後決定する。
- **Gatewayが再同期中であることを、接続中の利用者へ明示的に通知しなければならない。**
- General Viewは再同期状態を利用者が認識できる形で表示できなければならない。具体的なUI表現はView設計で決定する。
- 再同期完了後は、整合性を確認した状態から正規配信へ復帰する。

## 決定論との関係

- Gatewayの切断、再接続、再送、キャッシュ再構築、公開遅延バッファの揺らぎが、同一の有効Operation集合・順序・適用時刻に対するCoreの世界結果を変化させてはならない。
- Gateway数やMaster個体の違いを世界シミュレーションの乱数源や結果決定要因にしない。

## 今後決定が必要な事項

- キャッシュ同期に用いる具体的な同期識別情報
- 差分／全量同期の選択条件
- 再同期中に表示する世界状態の扱い
- 利用者へ通知する再同期状態のプロトコル表現
- 再同期完了判定
- 公開遅延バッファのConfig項目と既定値の正確な定義
- 長時間切断したGatewayが保持する未確認Operationの保持期限・扱い
